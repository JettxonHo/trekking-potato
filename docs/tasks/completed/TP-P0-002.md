## 调查阶段

调查确认：

- 原天气数组从请求当天开始，而不是用户选择的出发日期；
- `tripDays` 没有进入天气模块；
- 返回天气天数与行程天数没有确定性关系；
- 超出预报范围时，系统可能继续返回当前天气并以备注提示；
- Prompt、首日派生字段和前端会继续使用错误窗口。

## 最终实施

采用方案 A（增强版）：

1. 请求使用明确的 `start_date` 和 `end_date`；
2. `end_date = start_date + tripDays - 1`；
3. `tripDays` 入口使用严格类型白名单；
4. 出发日期早于产品时区当天时确定性拒绝；
5. API 返回日期必须与完整行程窗口逐项一致；
6. 部分覆盖映射为 `out_of_range`；
7. API 日期范围错误映射为 `out_of_range`；
8. 不使用当前天气替代无法获取的行程天气；
9. `confidence` 按真实预报提前量计算；
10. 保持原有 `m/s` 风速单位契约；
11. Prompt 和前端复用修正后的统一天气窗口。
