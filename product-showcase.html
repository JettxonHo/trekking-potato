01 / PROBLEM

路线已经确定，
判断却仍然悬空。

用户不是在找一篇“附近有什么好玩的”攻略。他已经选好了地方，真正缺的是：这条具体路线，在我的日期、时间和能力条件下，哪些事实会阻断出发，哪些准备必须补齐。

“今天能不能走”，不该由一段听起来笃定的生成文字决定。

所以产品机会不是增加更多内容，而是把判断拆成可核验的层次：先确认路线身份与变体，再锁定活动时段的天气窗口，最后用确定性规则合成结论；AI 只负责把已经成立的事实说清楚。

输入
路线、日期、每日出发时间、能力与攀登支持
输出
天气窗口、最低装备、风险原因、来源与四态结论
边界
不是官方预警、专业向导、医疗建议、救援或行中导航
02 / FLOW

先锁住可信事实，
再让解释发生。

流程里的每一次边界都对应一个产品决定：确认前没有天气、规则或 AI 副作用；结果先到，解释后到；历史只属于当前用户。

  1. 01

    搜索 / Search

    规范名、别名或模糊输入先进入服务端解析。候选只显示可确认的身份，不把客户端猜测当成路线事实。

  2. 02

    确认 / Confirm

    用户确认候选 ID 后才进入查询；未确认时零天气、零上下文、零 AI 副作用。永久 ID 由服务端重新取回。

  3. 03

    输入 / Input

    选择日期、每日出发时间、能力等级和必要的攀登支持。full Variant 的典型天数由目录固定，place-only 才允许 1–7 日。

  4. 04

    Base / 可信快照

    路线、逐日活动窗口、1–3 个天气采样点、最低装备、来源和确定性规则在同一服务端快照里汇合，先展示给用户。

  5. 05

    Advice + 私人历史

    Advice 只发送 queryId，AI 解释不能改写 BaseData。历史按微信 openid 私有隔离，可显式重试或清空。

THE HAND-OFF

两层真相，
一条清晰路径。

BaseData v2 负责回答“发生了什么、规则判定是什么”；Advice 负责回答“怎么理解它”。当天气不足或 AI 不可用，前一层仍然可见。

05 / TRUST LAYER

把“可信”变成
看得见的字段。

产品不是只返回一个颜色。用户可以回看路线变体、时间窗口、来源、最低装备与数据完整度，知道结果从哪里来，也知道哪里还没有被证明。

WEATHER / WINDOW

多采样点，按活动小时算

full Variant 按逐日 stage 连接 1–3 个天气采样点，使用 Asia/Shanghai、摄氏度、毫米和 m/s，只评估实际活动窗口。

  • 必要采样点失败，整体标为 insufficient
  • 不把夜间读数或被丢弃的部分窗口塞进结论
GEAR / RULES

最低装备先于 AI

路线类型、海拔、季节与能力条件经过确定性规则，输出 essential / recommended / optional 三组清单，可本地勾选但不写进可信上下文。

  • climb 不会被当作 trek 处理
  • AI 只能追加受限建议或解释
SOURCE / PROVENANCE

来源不是装饰信息

每条路线展示标题、发布方、A/B 等级、kind、核验日期和可选链接；官方管理事实与社区几何的责任边界分开记录。

  • 社区轨迹无公开 URL 时保持无链接
  • unknown 表示“尚未证明”，不是默认 open
QUERY / PRIVATE HISTORY

queryId 只做服务端钥匙

Advice 请求只发送服务端生成的 queryId；TripContext 绑定 openid，历史也只向当前用户开放，不保存 queryId。

  • 短期上下文过期时要求重新准备
  • 历史保存失败不污染本次结果，顺序重试使用 saveAttemptId
DETERMINISTIC / 可验证层

决定路线、天气、装备与 verdict

route identity、route type、fixedDays、operational status、hourly snapshot、reasons、minimumGear 与最终四态均来自服务端可信字段和纯规则。

AI / 解释层

解释已经成立的事实

AI 可补充 recommended / optional、风险说明与 notes；它不能增加天气、替换来源、覆盖装备、制造 verdict 或接收客户端伪造事实。

08 / HANDOFF

代码就绪，不等于
部署就绪。

这份档案的交付边界是可审阅的产品与代码证据。接下来需要一个单独授权的部署验证阶段，而不是把未发生的事情写进作品集。

把边界说清楚，本身也是产品质量。

  1. D01

    确定性规则拥有最终发言权

    go / caution / no_go / null 与路线、天气、最低装备属于可信层；AI 仅解释和补充。

  2. D02

    来源责任被拆开记录

    A 级管理资料决定禁行/限制，B 级经审阅轨迹只支持实际记录的几何；unknown 不等于 open。

  3. D03

    异常状态是产品的一部分

    天气不足、AI 失败、上下文过期、历史写入失败都有显式边界和有界恢复，不靠静默重试掩盖。

  4. D04

    这不是发布声明

    未连接真实 CloudBase、API 或 LLM，未完成真机运行时验证，也未邀请真实闭测用户。

下一阶段：部署验证

需由人工单独授权并建立 staging 边界，验证真实依赖，而不是把代码就绪误写成生产就绪。

  • 配置 staging CloudBase、AppID、secrets 与 openid 权限
  • 补做正常 DevTools / 真机 smoke test，刷新五条路线管理状态
  • 执行 TripContext v1 → v2 drain / cutover、索引与回滚检查
  • 通过后再决定是否启动 5–10 名目标用户的真实闭测
